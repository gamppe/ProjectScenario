## 노드와 연결

| 항목 | 이름 (현재 → 제안) | 설명 (현재 → 제안) |
|---|---|---|
| `node:vision` | 비전 → **프로젝트 목표** | 프로젝트가 풀 문제와 목표 → **해결할 문제와 목표, 만들지 않을 것** |
| `node:persona` | 사용자 | 누가 쓰는지 → **사용자와 사용자가 해내고 싶은 일** |
| `node:feature` | 기능 | 만들 기능 → **제품이 제공할 기능과 우선순위** |
| `node:story` | 스토리 → **사용자 이야기** | 사용자가 하고 싶은 일과 완료 기준 → **누가 무엇을 왜 원하는지와 완료 기준** |
| `node:screen` | 화면 | 화면 하나 → **화면 하나의 구성과 상태** |
| `node:interaction` | 상호작용 → **화면 동작** | 이걸 하면 이렇게 된다 → **사용자 행동에 따른 화면의 반응** |
| `node:flow` | 플로우 → **사용 흐름** | 사용자가 이동하는 흐름 → **사용자가 거치는 화면과 순서** |
| `node:entity` | 데이터 | 앱이 다루는 데이터 → **다루는 데이터와 그 안의 정보** |
| `node:decision` | 기술 결정 → **기술 선택** | 기술 선택과 그 이유 → **선택한 기술과 대안, 선택 이유** |
| `node:task` | 작업 | 구현할 작업 → **만들 작업의 순서와 완료 조건** |
| `node:risk` | 리스크 → **위험** | 걱정되는 위험 → **예상되는 위험과 영향, 대응 방법** |
| `node:folder` | 폴더 | 묶어 보관, 더블클릭해서 열기 → **기획 요소를 묶어 정리하고 진행 상황 확인** |
| `edge:contains` | 포함 | 부모와 자식으로 묶기 → **상위 항목 아래에 하위 항목 묶기** |
| `edge:implements` | 구현 | 작업이 기능을 구현함 → **작업이 만드는 기능이나 사용자 이야기 연결** |
| `edge:navigates` | 화면 이동 | 화면에서 화면으로 이동 → **한 화면에서 다른 화면으로 이동** |
| `edge:depends_on` | 선행 필요 | 먼저 끝나야 하는 것 → **한 작업 전에 끝나야 할 작업 연결** |
| `edge:uses_data` | 데이터 사용 | 화면이 쓰는 데이터 → **화면이나 기능이 사용하는 데이터 연결** |
| `edge:blocks` | 막음 → **진행 방해** | 진행을 막는 관계 → **다른 항목의 진행을 막는 관계 표시** |
| `edge:relates` | 관련 | 느슨한 연관 → **다른 연결에 속하지 않는 연관 표시** |

## 검토 의견 (적용 전에 보면 좋은 것)

### 좋은 점
- 질문 id와 선택지 `value`가 **모두 그대로**라서 저장된 답변과 코드가 깨지지 않습니다.
- 짧은 이름은 전부 12자 이내이고 서로 겹치지 않습니다. 예시도 3개 이하입니다.
- 전문용어가 많이 풀렸습니다. MVP, Non-goals, 엔티티, 토스트, 사이드바 같은 말이 사라졌고, 선택지 라벨(`offline` → "인터넷 연결이 끊김" 등)도 이해하기 쉬워졌습니다.
- 질문의 의미는 대부분 유지됩니다. 46개 중 44개는 문장을 다듬은 정도입니다.

### 적용하기 전에 고치는 게 좋은 곳

1. **`wireframes-key-screen` — 질문의 절반이 사라졌습니다.**
   현재는 "가장 중요한 화면은 무엇이고, 그 화면에 꼭 있어야 할 요소는 무엇인가요?"인데, 제안은 "가장 중요한 화면에는 어떤 요소가 꼭 있어야 하나요?"입니다. **어느 화면인지 묻지 않아서** 답에 화면 이름이 빠질 수 있고, AI 에이전트가 어떤 화면 얘기인지 알 수 없게 됩니다.
2. **`stack-constraints` — 답하기 어려워졌습니다.**
   현재 문구의 "라이선스, 성능, 보안 등"이 사라져서 "반드시 지켜야 할 제약 조건은 무엇인가요?"만 남았습니다. 힌트와 예시도 없어서 비개발자는 무엇을 적어야 할지 막막합니다. 예를 들어 "개인정보를 저장하지 않는다 / 인터넷 없이도 동작해야 한다" 같은 예시를 붙이는 게 좋겠습니다.
3. **노드 이름 2개가 6자 기준을 넘습니다.** "프로젝트 목표"(7자), "사용자 이야기"(7자). 그대로 적용하면 `labels.test.ts`의 6자 제한 테스트가 실패하고 리본 버튼이 더 넓어집니다. 기준을 7자로 풀거나 이름을 줄여야 합니다.
4. **`design-theme` 짧은 이름 "화면 밝기 모드".** "화면 밝기(밝기 조절)"와 헷갈릴 수 있고, 앱의 디자인 탭에 있는 **"테마"** 버튼과 용어가 달라집니다.
5. **`stack-language` — 어색한 새 단어.** "개발 틀(프레임워크)"은 처음 보는 표현이고, 짧은 이름 "개발 언어·도구"는 프레임워크보다 범위가 넓어집니다.
6. **`problem-goals` — "1~3개"가 사라졌습니다.** 목표를 많이 적지 않게 하려던 장치입니다. 의도적으로 뺀 것이면 괜찮습니다.

### 용어가 서로 어긋납니다 (제안서도 지적한 부분)
이번 요청에 **단계 이름(14개)은 들어 있지 않아서** 바뀌지 않았습니다. 그런데 노드와 질문 이름은 바뀌어서 같은 대상을 두 가지 말로 부르게 됩니다.

| 단계 이름 (그대로) | 새 노드/질문 이름 |
|---|---|
| 사용자 플로우 | 사용 흐름 / 주요 사용 흐름 |
| 사용자 스토리 | 사용자 이야기 |
| 상호작용 정의 | 화면 동작 |
| 리스크/가정 | 위험 |
| 기술 스택/아키텍처 | 기술 선택 / 개발 언어·도구 |
| 와이어프레임 | 화면 구성 느낌 / 핵심 화면 구성 |

내보내기 md(한국어 출력)의 제목("사용자 스토리", "리스크와 가정" 등)과 CLI 문구도 옛 용어 그대로입니다. 적용할 때는 **단계 이름과 md 제목까지 같이 정해야** 일관됩니다.

### 그 밖에 알아둘 점
- **예시가 거의 전부 "예약" 앱입니다.** 문제 정의, 목표, 스토리, 화면, 플로우, 상호작용, 데이터가 모두 같은 예약 서비스 예시입니다. "할 일 앱"에 치우쳤던 것을 "예약 앱"으로 바꾼 셈이라, 사용자가 예약 서비스 비슷하게 답할 수 있습니다.
- **폴더 설명은 옛 구조 기준입니다.** 제안은 "기획 요소를 묶어 정리하고 진행 상황 확인"인데, 이번에 폴더가 바뀌어서(안의 노드가 pill로 보이고, 더블클릭하면 안쪽 다이어그램이 열림) 이 설명에는 열기 동작이 없습니다. 폴더 설명은 따로 정하는 게 좋겠습니다.
- **말투가 조금 섞입니다.** 힌트 일부가 "~돼요", "~정해요"이고 나머지는 "~적어주세요"입니다.
- **한 질문이 두 가지를 묻는 곳이 남아 있습니다.** `users-context`(상황과 빈도), `wireframes-style`(밀도와 느낌), `tasks-first`(목표와 완료 기준). 제안서도 나누는 걸 검토하라고 적었습니다.

### 제안서의 「제안」 섹션 (아직 아무것도 하지 않음)
- **새 질문 후보 2개:** `users-frequency`("얼마나 자주 사용하나요?"), `security-personal-data`("개인정보를 다룬다면 어떻게 보호해야 하나요?")
- **나누면 좋다고 한 질문 4개:** `users-context`, `wireframes-key-screen`, `data-entities`, `tasks-first`
- **겹친다고 한 쌍:** `users-jobs`↔`stories-core`, `stories-core`↔`flows-main`, `wireframes-style`↔`design-tone`

질문을 새로 만들거나 나누려면 id 설계와 md 내보내기 연결(어디에 쓰일지)도 정해야 해서, 문구 적용과는 따로 결정하는 게 좋습니다.
