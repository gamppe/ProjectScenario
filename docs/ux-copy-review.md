## 0. 결정된 것: 스토리 노드 이름은 「요구사항」

제안서는 `스토리`를 `사용자 이야기`(7자)로 바꿨는데, 어색하다는 의견이 있어 **「요구사항」(4자)** 으로 정했습니다. 6자 제한도 지킵니다.
제안서 문구 중 「사용자 이야기」가 들어간 두 곳도 함께 바꿔야 합니다.

```diff
# node:story
# 이름
- 스토리
+ 요구사항
# 설명
- 사용자가 하고 싶은 일과 완료 기준
+ 사용자가 원하는 일과 완료 기준
```

```diff
# edge:implements
# 설명
- 작업이 기능을 구현함
+ 작업이 만드는 기능이나 요구사항 연결
```

> 기획 단계 이름 `사용자 스토리`와 질문의 짧은 이름, md 제목도 같은 말로 맞춰야 합니다. (아래 3번 참고)

## 1. 적용 전에 고치는 게 좋은 곳 (의미가 약해지거나 어색함)

#### 1-1. wireframes-key-screen — 어느 화면인지 묻는 절반이 사라짐

현재는 "가장 중요한 화면은 무엇이고, 그 화면에 꼭 있어야 할 요소는 무엇인가요?"인데, 제안은 화면 이름을 묻지 않습니다. 답에 화면 이름이 빠지면 AI 에이전트가 어떤 화면 얘기인지 알 수 없습니다.
**제안:** "가장 중요한 화면은 무엇이고, 거기에 꼭 있어야 할 요소는 무엇인가요?"로 되돌리거나 질문을 둘로 나누기.

```diff
# wireframes-key-screen
# 질문
- 가장 중요한 화면은 무엇이고, 그 화면에 꼭 있어야 할 요소는 무엇인가요?
+ 가장 중요한 화면에는 어떤 요소가 꼭 있어야 하나요?
# 짧은 이름
- 핵심 화면
+ 핵심 화면 구성
```

#### 1-2. stack-constraints — 무엇을 적을지 막막해짐

"라이선스, 성능, 보안 등"이라는 단서가 사라지고 힌트·예시도 없습니다. 비개발자는 제약 조건이 뭔지 모릅니다.
**제안:** 예시를 붙이기. 예) 개인정보를 저장하지 않는다 / 인터넷 없이도 동작해야 한다 / 무료 라이선스만 쓴다.

```diff
# stack-constraints
# 질문
- 라이선스, 성능, 보안 등 지켜야 할 제약이 있나요?
+ 프로젝트에서 반드시 지켜야 할 제약 조건은 무엇인가요?
```

#### 1-3. design-theme — 짧은 이름 "화면 밝기 모드"

"화면 밝기(밝기 조절)"와 헷갈릴 수 있고, 앱의 디자인 탭에 있는 **"테마"** 버튼과 용어가 달라집니다.
**제안:** 짧은 이름은 "테마"(또는 "밝은/어두운 화면")로 유지.

```diff
# design-theme
# 질문
- 라이트/다크 테마는 어떻게 하나요?
+ 화면의 밝은 모드와 어두운 모드를 어떻게 제공하나요?
# 짧은 이름
- 테마
+ 화면 밝기 모드
# 선택지
- light=라이트만, dark=다크만, both=둘 다
+ light=밝은 모드만, dark=어두운 모드만, both=밝은 모드와 어두운 모드 모두
```

#### 1-4. stack-language — 어색한 새 단어

"개발 틀(프레임워크)"은 처음 보는 표현이고, 짧은 이름 "개발 언어·도구"는 프레임워크보다 범위가 넓습니다.
**제안:** "프로그래밍 언어와 프레임워크(개발에 쓰는 기본 도구)".

```diff
# stack-language
# 질문
- 주 사용 언어와 프레임워크는 무엇인가요?
+ 주로 사용할 프로그래밍 언어와 개발 틀(프레임워크)은 무엇인가요?
# 짧은 이름
- 언어/프레임워크
+ 개발 언어·도구
# 예시
- TypeScript + React + Vite
+ TypeScript와 React, Vite
```

#### 1-5. problem-goals — "1~3개" 제한이 사라짐

목표를 많이 적지 않게 하려던 장치였습니다. 의도적으로 뺀 것이면 괜찮습니다.

```diff
# problem-goals
# 질문
- 이 프로젝트의 핵심 목표 1~3개는 무엇인가요?
+ 이 프로젝트에서 이루고 싶은 핵심 목표는 무엇인가요?
```

#### 1-6. 선택지 라벨의 의미가 살짝 달라진 곳

`offline`이 "앱이 인터넷 없이도 동작"이라는 뜻인데 "인터넷 연결이 끊김"(상태)으로 바뀌었습니다. `cli`를 "명령어 입력 화면"이라 부르는데 CLI는 화면이 아닙니다.
**제안:** offline="인터넷이 없어도 쓸 수 있음", cli="명령어로 실행(터미널)".

```diff
# interactions-states
# 선택지
- loading=로딩 중, empty=비어 있음, error=오류, offline=오프라인
+ loading=불러오는 중, empty=내용이 없음, error=오류가 발생함, offline=인터넷 연결이 끊김
```

```diff
# stack-platform
# 선택지
- web=웹, windows=Windows 데스크톱, mobile=모바일, cli=CLI
+ web=웹 브라우저, windows=윈도우 컴퓨터, mobile=모바일 기기, cli=명령어 입력 화면
```


## 2. 노드 이름 길이 (6자 기준)

#### 2-1. node:vision "프로젝트 목표"(7자)

6자를 넘고 리본 버튼이 넓어집니다. 비전 노드는 "해결할 문제 + 목표 + 만들지 않을 것"을 담는데 이름은 "목표"만 말합니다.
**제안:** "프로젝트"(4자) 또는 "목표"(2자). (또는 기준을 7자로 완화)

```diff
# node:vision
# 이름
- 비전
+ 프로젝트 목표
# 설명
- 프로젝트가 풀 문제와 목표
+ 해결할 문제와 목표, 만들지 않을 것
```

(`node:story`의 7자 문제는 0번의 「요구사항」으로 해결됩니다.)

## 3. 용어가 서로 어긋남 (제안서도 지적한 부분)

이번 요청에 **기획 단계 이름 14개는 들어 있지 않아서** 그대로입니다. 그런데 노드와 질문 이름은 바뀌어서 같은 대상을 두 가지 말로 부르게 됩니다.

| 기획 단계 이름 (그대로) | 새 노드/질문 이름 |
|---|---|
| 사용자 플로우 | 사용 흐름(노드) / 주요 사용 흐름(질문) |
| 사용자 스토리 | **요구사항(노드)** |
| 상호작용 정의 | 화면 동작(노드, 질문) |
| 리스크/가정 | 위험(노드) / 주요 위험(질문) |
| 기술 스택/아키텍처 | 기술 선택(노드) / 개발 언어·도구(질문) |
| 와이어프레임 | 화면 구성 느낌 / 핵심 화면 구성(질문) |

내보내기 md(한국어 출력)의 제목("사용자 스토리", "리스크와 가정" 등)과 CLI 문구도 옛 용어입니다. **적용할 때 단계 이름과 md 제목까지 같이 정해야** 합니다.

## 4. 그 밖에 알아둘 점

#### 4-1. 예시가 거의 전부 "예약" 앱

문제 정의, 목표, 스토리, 화면, 플로우, 상호작용, 데이터가 모두 같은 예약 서비스 예시입니다. "할 일 앱" 편중이 "예약 앱" 편중으로 바뀐 셈이라 사용자가 예약 서비스 비슷하게 답할 수 있습니다. 질문마다 다른 분야(가계부, 운동 기록, 학습 앱 등)를 섞는 것이 좋습니다.

```diff
# problem-statement
# 예시
- 기존 할 일 앱은 너무 무거워서 빠른 메모용으로 쓰기 어렵다.
+ 자영업자는 예약 전화를 받느라 손님 응대에 집중하기 어렵다.
```

```diff
# problem-goals
# 예시
- 할 일을 3초 안에 추가한다
+ 손님이 온라인으로 예약할 수 있다 / 예약 확인에 걸리는 시간을 줄인다
```

```diff
# stories-core
# 예시
- 앱을 열고 → 할 일을 입력하고 → 완료로 체크한다
+ 가게를 찾는다 → 날짜를 고른다 → 예약한다
```

```diff
# ia-screens
# 예시
- 목록 / 상세 / 설정
+ 예약 목록 / 예약 상세 / 설정
```

```diff
# flows-main
# 예시
- 목록 → (입력) → 목록에 추가됨 → 상세 → 완료 처리
+ 가게 목록 → 가게 상세 → 예약 화면 → 예약 완료 화면
```

```diff
# interactions-key
# 예시
- Enter를 누르면 → 할 일이 추가되고 입력창이 비워진다
+ 예약 버튼을 누르면 → 예약 확인 화면이 열린다
```

```diff
# data-entities
# 예시
- 할 일: 제목, 완료 여부, 마감일
+ 예약: 손님 이름, 날짜, 인원
```

#### 4-2. 폴더 설명은 옛 구조 기준

제안은 "기획 요소를 묶어 정리하고 진행 상황 확인"입니다. 지금 폴더는 "안의 노드가 한 줄 알약으로 나열되고, 더블클릭하면 안쪽 다이어그램이 열리는" 구조라 열기 동작이 빠져 있습니다.
**제안:** "묶어 보관, 더블클릭해서 열기"(현재 문구)를 유지하거나 "노드를 담고, 더블클릭하면 안쪽이 열림".

```diff
# node:folder
# 설명
- 묶어 보관, 더블클릭해서 열기
+ 기획 요소를 묶어 정리하고 진행 상황 확인
```

힌트 일부가 "~돼요", "~정해요"이고 나머지는 "~적어주세요"입니다. 한쪽으로 통일하면 좋습니다.

```diff
+ AI가 요청하지 않은 기능까지 만드는 것을 막는 데 도움이 돼요.
```

```diff
# interactions-states
# 힌트
- 고르지 않은 상태는 AI 에이전트가 임의로 채우게 됩니다.
+ 고르지 않은 상태는 AI가 알아서 정해요.
```

#### 4-4. 한 질문이 두 가지를 묻는 곳이 남아 있음

`users-context`(상황과 빈도), `wireframes-style`(밀도와 느낌), `tasks-first`(목표와 완료 기준). 제안서도 나누는 걸 검토하라고 적었습니다.

```diff
# users-context
# 질문
- 어떤 상황에서, 얼마나 자주 쓰게 되나요?
+ 주요 사용자는 어떤 상황에서 얼마나 자주 이 제품을 사용하나요?
```

```diff
# wireframes-style
# 질문
- 화면의 전체적인 밀도와 느낌은 어떤가요?
+ 화면에 정보를 얼마나 빽빽하게 배치하고 어떤 느낌을 주고 싶나요?
```

```diff
# tasks-first
# 질문
- 첫 번째 마일스톤은 무엇이고, 어떤 상태면 끝난 건가요?
+ 첫 번째로 완성할 목표와 그 완료 기준은 무엇인가요?
```


## 5. 좋은 점 (그대로 받아도 되는 부분)

- 질문 id와 선택지 `value`가 **모두 그대로**라서 저장된 답변과 코드가 깨지지 않습니다.
- 짧은 이름은 전부 12자 이내이고 서로 겹치지 않으며, 예시는 3개 이하입니다.
- MVP, Non-goals, 엔티티, 토스트, 사이드바 같은 전문용어가 풀렸습니다.
- 46개 중 대부분(약 44개)은 문장을 다듬은 정도라 의미가 유지됩니다.

## 6. 제안서의 「제안」 섹션 (적용 여부를 따로 결정)

- **새 질문 후보 2개:** `users-frequency`("얼마나 자주 사용하나요?"), `security-personal-data`("개인정보를 다룬다면 어떻게 보호해야 하나요?")
- **나누면 좋다고 한 질문 4개:** `users-context`, `wireframes-key-screen`, `data-entities`, `tasks-first`
- **겹친다고 한 쌍:** `users-jobs`↔`stories-core`, `stories-core`↔`flows-main`, `wireframes-style`↔`design-tone`

질문을 새로 만들거나 나누려면 id 설계와 md 내보내기 연결(어디에 쓰일지)도 정해야 해서, 문구 적용과는 따로 결정하는 게 좋습니다.
